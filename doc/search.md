# Search

## Introduction

rosa2 provides full-text and faceted search over manuscript collection data through an Opensearch backend. The search system combines three components:

1. **Static IIIF Presentation 3.0 files** — generated by `generate-iiif-pres`, these contain collection and manifest data that can be served by any static web server.
2. **Per-collection `service/jhsearch.json` files** — describe the available search fields, categories, and default fields for each collection, enabling clients to build search interfaces dynamically.
3. **Opensearch backend** — provides the actual search engine with full-text queries, language-specific analysis, and keyword faceting via the Opensearch Bulk API.

## IIIF Search Service

The JHSearch service is advertised as a custom IIIF Presentation 3.0 service on collections and manifests. When the `--opensearch-url` option is provided to `generate-iiif-pres`, each generated collection and manifest includes a `service` entry pointing to a per-collection `service/jhsearch.json` file. This file describes the available search fields, facet categories, and the Opensearch endpoint for direct queries.

### Service Definition

Each collection and manifest includes a service entry following the IIIF Presentation 3.0 `service` property pattern:

- **Type**: `JHSearchService2`
- **Profile**: `https://github.com/jhu-digital-manuscripts/rosa2/doc/search.md`
- **ID**: The URL of the collection's `service/jhsearch.json` file

### Example Service Reference in a Collection

```json
{
  "@context": "http://iiif.io/api/presentation/3/context.json",
  "id": "https://iiif.example.org/aor/collection",
  "type": "Collection",
  "label": { "en": ["Archaeology of Reading"] },
  "service": [
    {
      "id": "https://iiif.example.org/aor/service/jhsearch",
      "type": "JHSearchService2",
      "profile": "https://github.com/jhu-digital-manuscripts/rosa2/doc/search.md"
    }
  ],
  "items": [...]
}
```

### `service/jhsearch.json` Structure

The `service/jhsearch.json` file is a static JSON file generated per collection. Clients dereference the service `id` to retrieve it. Its structure:

```json
{
  "fields": [
    {
      "name": "marginalia",
      "label": "Marginalia",
      "description": "Notes written by a reader.",
      "subfields": ["en", "fr", "la", "it", "el", "es", "de", "ofr", "keyword"]
    },
    {
      "name": "mark",
      "label": "Mark",
      "description": "Pen marks made on a page...",
      "subfields": ["en", "fr", "la", "it", "el", "es", "de", "ofr", "keyword"],
      "values": [
        { "value": "plus_sign", "label": "Plus Sign" },
        { "value": "dash", "label": "Dash" }
      ]
    },
    {
      "name": "method",
      "label": "Method",
      "description": "Implement used to create mark or underline.",
      "values": [
        { "value": "pen", "label": "Pen" },
        { "value": "chalk", "label": "Chalk" }
      ]
    },
    {
      "name": "people",
      "label": "People",
      "description": "Search for names of people within metadata and transcriptions."
    }
  ],
  "categories": [
    { "name": "authors", "label": "Author" },
    { "name": "current_location", "label": "Current Location" },
    { "name": "date", "label": "Date" }
  ],
  "default-fields": ["marginalia", "mark", "method", "people"],
  "opensearch": "https://search.example.org/_search"
}
```

| Key | Description |
|-----|-------------|
| `fields` | Array of searchable fields. Each has `name`, `label`, `description`, optional `subfields` (language sub-field names), and optional `values` (enumerated values). |
| `fields[].name` | The Opensearch field name. For fields with subfields, query as `name.subfield` (e.g., `marginalia.en`, `mark.keyword`). |
| `fields[].subfields` | Array of sub-field names. Includes language codes for text search and `keyword` for type/name lookup. |
| `fields[].values` | Array of `{value, label}` pairs for fields with enumerated keyword values (searched via `field.keyword`). |
| `categories` | Array of facet categories. Each `name` is an Opensearch keyword field suitable for `terms` aggregations. |
| `default-fields` | Array of field names searched when no explicit field is specified in the query. |
| `opensearch` | The Opensearch `_search` endpoint URL that clients can query directly. |

### Client Workflow

1. Load a collection or manifest from the IIIF static files.
2. Find the `JHSearchService2` entry in the `service` array.
3. Dereference the service `id` to fetch `service/jhsearch.json`.
4. Use the `fields` and `categories` to build a search UI.
5. For fields with `subfields`, construct queries against `fieldName.subfield` (e.g., `marginalia.en`, `mark.keyword`).
6. For fields with `values`, present enumerated options and query `field.keyword: "value"`.
7. Send queries to the `opensearch` endpoint using the Opensearch query DSL.

## Index Structure

The system uses two Opensearch indexes, each defined in the `opensearch/` directory at the repository root:

| Index | Definition File | Description |
|-------|----------------|-------------|
| `manifest` | `opensearch/manifest.json` | One document per book — bibliographic metadata, identifiers, and keyword facet fields |
| `canvas` | `opensearch/canvas.json` | One document per page — page-level data with all annotations merged in |

All annotation data targeting a canvas is accumulated into the canvas document. Each annotation type has its own independently searchable field, allowing users to search within specific annotation types (e.g. only marginalia, only marks) without needing a separate annotations index.

### `manifest` Index

Book-level metadata for full-text search and faceted filtering. Key fields:
- `id` — unique manifest ID (`{collection_id}.{book_id}`, e.g. `rose.Douce195`)
- `label` — the human-readable common name of the book
- `title` — multi-language title field (common name + BookText titles)
- `collection_id` — array of all ancestor collection IDs
- `thumbnail` — up to 3 canvas IDs for representative thumbnails
- `logo` — logo image filename
- Faceting fields: `authors`, `type`, `current_location`, `date`, `num_illustrations`, etc.

### `canvas` Index

Page-level data with all annotations merged in. Key structural fields:
- `id` — unique canvas ID (`{collection_id}.{image_id_no_ext}`, e.g. `aor.Ha2.001r`)
- `manifest_id` — parent manifest ID (`{collection_id}.{book_id}`, e.g. `aor.Ha2`)
- `collection_id` — array of all ancestor collection IDs
- `label` — page label (pagination/signature/name)
- `page_num` — 0-based page position (maps to IIIF canvas URI `/canvas/{page_num}`)

Per-type annotation fields (multi-language text objects):
- `marginalia`, `underline`, `mark`, `symbol`, `errata`, `numeral`, `drawing`, `emphasis`, `cross_reference`, `calculation`, `graph`, `table`, `transcription`, `illustration`, `translation`, `anchor_text`

Keyword array fields:
- `people`, `books`, `locations`, `symbols`, `method`, `hand`, `annotator`, `language`, `marginalia_language`, `topic`, `char_name`

See `doc/opensearch-indexes.md` for complete field definitions.

## Multi-Language Text Analysis

Textual content is routed into language-specific sub-fields so that the correct analyzer (stemming, stop words) is applied at index time. The sub-field naming convention is:

```
field_name.language_code
```

For example, marginalia written in Latin is indexed as `marginalia.la`, while a French underline goes to `underline.fr`.

### Supported Languages

| Sub-field | Language | Analyzer |
|-----------|----------|----------|
| `.en` | English | Built-in `english` (stemming + stop words) |
| `.fr` | French | Built-in `french` (stemming + stop words) |
| `.ofr` | Old French | Custom: French stemming + ASCII folding |
| `.la` | Latin | Custom: standard tokenizer + ASCII folding |
| `.it` | Italian | Built-in `italian` |
| `.el` | Greek | Built-in `greek` |
| `.es` | Spanish | Built-in `spanish` |
| `.de` | German | Built-in `german` |

### Keyword Sub-Field Pattern

Fields like `mark`, `symbol`, `drawing`, `calculation`, `graph`, and `table` contain both enumerated keyword values and free text. They use a `.keyword` sub-field:

- `mark.keyword` — the mark type name (e.g. `"plus_sign"`)
- `mark.en` — the mark's referenced text in English
- `symbol.keyword` — the symbol name (e.g. `"Jupiter"`)
- `drawing.keyword` — the drawing type (e.g. `"manicule"`)

### Language Fallback

If content has a language code not in the supported set, it is routed to the `.en` (English) sub-field.

## Generating Search Data

### Step 1: Generate IIIF Presentation Files

```bash
java -jar rosa2.jar generate-iiif-pres \
  --archive /data/archive \
  --output /deploy/iiif \
  --base-url https://iiif.example.org \
  --image-base-url https://image.example.org/iiif/ \
  --image-api-version 2 \
  --opensearch-url https://search.example.org/_search
```

When `--opensearch-url` is provided:
- Each collection gets a `service/jhsearch.json` file
- Collection and manifest JSON include `service` entries referencing it

### Step 2: Generate Opensearch Bulk Ingest Files

```bash
java -jar rosa2.jar generate-opensearch-ingest \
  --archive /data/archive \
  --output /deploy/bulk
```

Produces one `<collection-id>.bulk.json` file per collection. Each file uses the Opensearch Bulk API format — alternating action and document lines (NDJSON):

```json
{"index":{"_index":"canvas","_id":"aor.Ha2.001r"}}
{"id":"aor.Ha2.001r","manifest_id":"aor.Ha2","collection_id":["aor","top"],"label":"1r","page_num":0,"marginalia.la":"verbum","mark.keyword":"plus_sign",...}
```

### Step 3: Create Indexes

```bash
curl -X PUT "https://<host>:9200/manifest" \
  -H "Content-Type: application/json" \
  -d @opensearch/manifest.json

curl -X PUT "https://<host>:9200/canvas" \
  -H "Content-Type: application/json" \
  -d @opensearch/canvas.json
```

### Step 4: Ingest Bulk Data

```bash
for f in /deploy/bulk/*.bulk.json; do
  curl -X POST "https://<host>:9200/_bulk" \
    -H "Content-Type: application/x-ndjson" \
    --data-binary @"$f"
done
```

## Example Queries

### Search Marginalia for a Specific Term

```json
{
  "query": {
    "match": { "marginalia.en": "astronomy" }
  }
}
```

### Search for a Specific Mark Type

```json
{
  "query": {
    "term": { "mark.keyword": "plus_sign" }
  }
}
```

### Search Mark Text Content

```json
{
  "query": {
    "multi_match": {
      "query": "important passage",
      "fields": ["mark.en", "mark.la", "mark.fr"]
    }
  }
}
```

### Cross-Field Search Across Multiple Annotation Types

```json
{
  "query": {
    "multi_match": {
      "query": "philosophia naturalis",
      "fields": [
        "marginalia.la",
        "underline.la",
        "cross_reference.la",
        "drawing.la",
        "graph.la",
        "table.la"
      ],
      "type": "best_fields"
    }
  }
}
```

### Faceted Search with Aggregations

Filter by annotator with aggregations on method and language:

```json
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "annotator": "John Dee" } }
      ]
    }
  },
  "aggs": {
    "methods": { "terms": { "field": "method" } },
    "languages": { "terms": { "field": "marginalia_language" } }
  }
}
```

### Manifest Search with Facets

```json
{
  "query": {
    "bool": {
      "filter": [
        { "term": { "current_location": "London" } }
      ],
      "must": [
        { "multi_match": { "query": "rhetoric", "fields": ["title.en", "title.la"] } }
      ]
    }
  },
  "aggs": {
    "authors": { "terms": { "field": "authors" } }
  }
}
```

### Canvas Lookup by ID

Find a specific canvas document:

```json
{
  "query": {
    "term": { "id": "aor.Ha2.003r" }
  }
}
```

### Find All Canvases for a Manifest

```json
{
  "query": {
    "term": { "manifest_id": "aor.Ha2" }
  },
  "sort": [{ "page_num": "asc" }]
}
```

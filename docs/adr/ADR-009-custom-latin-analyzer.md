# ADR-009: Custom Latin analyzer via stemmer_override with character normalization

**Date:** 2026-10-14
**Status:** Accepted
**Deciders:** rosa2 maintainers
**Supersedes:** N/A

> Retroactive record of a decision already embodied in the codebase.

## Context and Problem Statement

A large share of the annotation and transcription text is Latin. Latin has rich
morphology (extensive declensions and conjugations) and early-modern spelling
variation, but Opensearch ships no Latin stemmer. Searching Latin without
lemmatization gives poor recall (an inflected form will not match its headword).
We needed language-appropriate Latin analysis within the per-language sub-field
strategy (ADR-003).

## Decision Drivers

- Match inflected Latin forms to their dictionary headword (true lemmatization).
- Handle classical-vs-modern orthography (`u`/`v`, `j`/`i`, ligatures, long s).
- Build only on token filters available in Opensearch 3.x.
- Keep the rule data reproducible from source.

## Considered Options

1. A custom `latin` analyzer: a `mapping` char_filter normalizes orthography (v→u, j→i, ligatures, long s), then a `stemmer_override` filter applies a generated lemma table (~29,760 rules covering ~1.38M inflected forms).
2. Stop-words-only Latin configuration (remove function words, no stemming).
3. Treat Latin with the standard analyzer, i.e. no Latin-specific handling.

## Decision Outcome

**Chosen option:** Option 1. The `latin` analyzer normalizes characters first
(`latin-charmap.txt`), so text matches the lemma table regardless of `u`/`v`
convention, then lemmatizes via `stemmer_override` with `latin-stemmer-rules.txt`,
regenerated by `generate_latin_stemmer_rules.py`. A stop-words-only fallback is
documented for environments where the rules file cannot be installed. Both rely
only on filters whose behavior is identical across Opensearch 2.x and 3.x.

### Positive Consequences

- Inflected Latin forms match their headwords, substantially improving recall.
- Orthographic variation (classical vs modern) no longer defeats matches.
- The rules file is reproducible from the generator script, not hand-maintained.

### Negative Consequences

- The analyzer depends on resource files installed and readable by Opensearch; a missing/unreadable file makes index creation fail (and silently falls back to dynamic mappings if that failure is ignored — see ADR-002/ADR-004 operational notes).
- Opensearch analyzers are not `updateable`, so a dictionary change requires rebuilding the indexes (`init-opensearch.sh`).
- On AWS the dictionaries are packaged as custom packages by ID; `init-opensearch.sh` rewrites the checked-in local-dev paths at deploy time.

## Options Analysis

### Option 1: stemmer_override + char normalization
Pros: true lemmatization; handles orthography; reproducible rules. | Cons: resource-file dependency; rebuild on dictionary change.

### Option 2: Stop-words only
Pros: no large rules file. | Cons: no stemming, so inflected forms still miss their headword.

### Option 3: Standard analyzer, no Latin handling
Pros: nothing to maintain. | Cons: worst recall; ignores the morphology that makes Latin search hard.
